## Release Decision Validation
- `ReleaseDecisionExecutionValidator` enforces strict verification of the persisted `EngineDecision`:
  - Must exist by exact `releaseDecisionId`.
  - `engineType == EngineType.RELEASE`.
  - `decision == DecisionStatus.ALLOW`.
  - `evaluationOutcome == EvaluationOutcome.SUCCESS`.
  - `subjectType == "MILESTONE"`.
  - `subjectId != null` and `organizationId != null`.
  - `inputFingerprint` and `decisionFingerprint` must be valid 64-character lowercase hex strings.
  - Decision must not be expired (`validUntil == null` or `validUntil.isAfter(Instant.now())`).
  - Active platform deterministic policy binding matching `FINX_RELEASE_DETERMINISTIC_BASE:1.0.0` content hash.

## Latest Decision Rule
- The release decision must be the most recent `RELEASE` decision for the buyer organization and milestone:
  - Validated via `EngineDecisionRepository.findFirstByOrganizationIdAndEngineTypeAndSubjectTypeAndSubjectIdOrderByEvaluatedAtDesc(...)`.
  - If a newer decision exists (even if also `ALLOW`), the older decision is considered stale and fails closed.

## Request Hash
- Deterministic collision-resistant SHA-256 fingerprint generated by `ReleaseInstructionRequestFingerprint`:
  - Canonical length-prefixed encoding over: `organizationId`, `dealId`, `milestoneId`, `releaseDecisionId`, `decisionFingerprint`, `inputFingerprint`, `policyVersionId`, `policyContentHash`, `beneficiaryBankAccountId`, `provider`, `providerAccountId`, `amount` (`stripTrailingZeros().toPlainString()`), and uppercase `currency`.

## Creation Idempotency
- Replay with identical idempotency key and matching request hash returns existing instruction.
- Replay with identical idempotency key but conflicting payload fails closed.
- Replay for the same release decision with identical derived parameters returns existing instruction.

## Escrow Reservation
- Calculated under `EscrowAccount` row lock:
  $$\text{activeReserved} = \sum \text{ReleaseReservation(ACTIVE for escrow)}$$
  $$\text{availableToReserve} = \text{escrowAccount.balance} - \text{activeReserved}$$
- Uses exact `BigDecimal` arithmetic.
- Requires $\text{availableToReserve} \ge \text{instruction.amount}$.
- Insufficient funds aborts with `IllegalStateException` and rolls back the transaction.

## Atomicity
- Single local database transaction (TX2) under `REPEATABLE_READ`:
  - `ReleaseInstruction`: `CREATED -> AUTHORIZED -> RESERVED`.
  - `ReleaseReservation`: exactly 1 row created in `ACTIVE` status.
  - Automatic concurrency conflict retry in `ReleaseAuthorizationService` handles transient PostgreSQL serialization conflicts.
  - If reservation fails, entire transaction rolls back; instruction remains `CREATED`.

## Concurrency
- **Concurrent Same Instruction**:
  - Multiple concurrent calls on same instruction serialize on pessimistic locks.
  - One thread transitions and commits `RESERVED` + 1 `ACTIVE` reservation.
  - Concurrent threads detect committed `RESERVED` state and return the existing reservation idempotently.
  - Verified on PostgreSQL: **PASS** (`activeCount == 1`).
- **Concurrent Oversubscription**:
  - Two concurrent milestones totaling 140,000 against escrow balance 100,000.
  - Serialized by `EscrowAccount` pessimistic row lock.
  - Exactly ONE reservation succeeds (70,000); second fails with insufficient available funds.
  - Active reservations sum equals 70,000 (never 140,000). Available funds = 30,000 (never negative).
  - Verified on PostgreSQL: **PASS**.
